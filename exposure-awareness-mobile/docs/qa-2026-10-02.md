# QA/QC: security, engine, accessibility, usability, calibration, stickiness

*2026-10-02. First full pass since the calm-mode/big-stones launch build and since the app went live at
[jasonjessewang.github.io/tox-tool](https://jasonjessewang.github.io/tox-tool/). Scope: the six areas asked for --
security/profile/data leakage, engine stability and accuracy, UI friendliness and accessibility, ease of use and score
calibration, and "stickiness" (read against this project's own calm-by-design invariant, not as a request to add
engagement mechanics -- see CLAUDE.md invariant 7). Three real bugs found and fixed, all verified; everything else
checked out clean or is a judgment call flagged below, not a defect.*

Checks after everything in this pass: 572 mobile tests (49 of them new), 31 backend tests (3 new), 33 Python tests,
TypeScript clean, 79/79 simulation invariants with the big-stones content active.

## 1. Security, profile data, and what can leak

**Reviewed:** every `fetch(...)` call in the app (6, matching exactly what About You's "What leaves this device"
panel claims -- barcode number, coordinates, nothing else); the backend's auth (SHA-256-hashed API keys, scoped
read/write), its OAuth token encryption (AES-256-GCM, HMAC-signed and time-limited `state`, timing-safe comparison),
every SQL query (table/column names are always a fixed, hardcoded list -- never built from a request -- and every
value is a bound parameter; no injection surface), the OCR endpoint (tesseract.js, no shell-out, magic-byte and
size validation before a photo ever reaches the WASM worker), `npm audit` on both projects, and the live site itself
for anything that shouldn't be exposed.

**Found and fixed:**

- **The backend API key lived in plain AsyncStorage/localStorage**, the same tier as every other, non-sensitive
  setting -- unlike everything else the app stores, this one is a real credential with write access to whatever
  backend is configured. Added `expo-secure-store` (OS keychain on iOS/Android; it has no web build at all, confirmed
  against its own SDK 57 docs, so web correctly keeps using AsyncStorage, same as before) behind a tiny
  platform-branching wrapper (`src/services/secureStorage.ts`, 5 new tests covering both paths) and pointed
  `backend.ts` at it. Costs nothing on web (unchanged there); real hardening once a native build exists.
- **No CORS handling on the backend at all**, which doesn't look like a hole (no CORS headers is the *more*
  restrictive default) but is a real functional bug: the web build of the app -- now a live, public site -- has no
  way to reach anyone's self-hosted backend on a different origin; the browser blocks the response before the app
  ever sees it. Added a small, explicit CORS middleware (`src/cors.ts`, 3 new tests) that reflects the caller's
  origin; safe to be permissive here specifically because this is a single-tenant server you run for yourself, not
  multi-tenant SaaS, and every route is already behind a Bearer API key that a browser never attaches to a
  cross-origin request on its own (unlike a cookie).

**Checked and genuinely clean, not just unexamined:** no `dangerouslySetInnerHTML`/`innerHTML`/`eval`, no
console-logged user data, no secret or token anywhere in the committed source (scanned the whole public repo, not
just this session's diff), no profile or health field (age, sex, conditions, pregnancy) ever reaches a URL or a
network call, the live GitHub Pages deploy serves exactly the exported bundle and nothing from source control
(`.sim-out`, `scripts/`, `package.json`, `.git/config` all 404 on the live site, as they should). Backend:
`npm audit` is clean (0). Mobile: `npm audit` shows 10 moderate findings, all the same underlying advisory (a
buffer-bounds issue in the `uuid` package, exploitable only when a caller supplies its own buffer to `uuid.v3/v5/v6`)
pulled in transitively by Expo's own build tooling (`@expo/config-plugins`, `@expo/metro-config`, ...) -- dev-time
only, never shipped in the bundle a user downloads, and not a pattern this project's own code uses. Not force-fixed:
`npm audit fix --force` would downgrade Expo itself for a risk that doesn't apply here.

## 2. Engine stability and accuracy

**Reviewed:** the full simulation (four lives, 84 days each, in their own timezones) with the big-stones content
live; the exposure signal's actual scoring math; the big-stones substances' citations and framing; the reordered
Starter Journey.

**Result: 79/79 invariants pass.** Score ranges, daily/weekly movement, and coverage-fill rates are essentially
unchanged from the pre-launch-build run (wellness means 59-91 across the four lives, same as before; largest
single-day move 7, largest weekly move 15) -- five new concern-level-3 substances and a bumped PM2.5 did not
destabilize calibration.

**Specifically checked, because it's the obvious place a "big stones" pass could go wrong:** does a single logged
mention of something now flagged at the top concern tier (a glass of wine at dinner; "alcohol" is now concern level
3) crater the score the way a sustained pattern should, but an occasional one shouldn't? No -- the exposure signal
is computed as flagged points *per entry* (a density over decayed, recency-weighted entries, confidence-shrunk
toward a typical pattern until there's enough to trust), not a cumulative point total, so one occasional entry among
a normal week of logging moves the reading proportionately, not catastrophically. This was already the design from
before the soak-run fixes; it held up under the new content without any change needed.

**Content check:** read the alcohol entry in full (new in this pass) against what a toxicologist would expect --
IARC Group 1 classification for ethanol and its acetaldehyde metabolite (correct), a real dose-response meta-analysis
and the GBD 2016 global burden analysis (PMIDs verified present, not just cited), dose-response framing rather than
a binary "any amount is equally bad," a separate pregnancy note, and a technical note on the ALDH2 polymorphism
(the East Asian "flushing" variant) that correctly explains *why* per-drink risk differs by genotype. Scientifically
sound, appropriately caveated, not alarmist.

**Also checked:** the Starter Journey's reordering reconciles "big stones first" with "easy first step" well --
radon (#1) and secondhand smoke (#2) lead by actual impact, but each one's *first* action is still a cheap,
low-effort measurement or awareness step ("order a $15-25 test kit," "find out when your home was built"), not an
expensive intervention; the smoke-free step adds a quit-line number without any judgment of the person. No issue
found here worth a fix -- noted as a strength.

## 3. UI friendliness and accessibility

Walked all 38 reachable screens with `scripts/a11y-audit.js` (headings, unnamed or repeated controls, targets under
24px, contrast under 4.5:1, text under 11px, missing `aria-checked`/`aria-selected` state) against a history-rich
simulated person, at phone width, on the real dev build with this session's fixes applied.

**Result: clean across the board** -- same standard as the 2026-09-26 walkthrough, confirming the calm-mode rewrite
(JourneyScreen, DashboardScreen, IntroScreen, plant.ts, quests.ts all meaningfully rewritten) didn't regress
anything the earlier pass had fixed.

**Found and fixed, both from actually looking at the rendered screens, not from the automated pass alone:**

- **"Full-grown · Full-grown. It bears fruit..."** on the Journey hub and the Dashboard's plant card -- the plant's
  stage label and its status message both started with "Full-grown," and every place that shows the message already
  shows the stage label right next to it, so they collided into an obviously-duplicated sentence. Fixed at the
  source (`engine/plant.ts`): the mature-stage messages no longer restate the stage name.
- **Two identically-named "PubMed ›" links** (and a matching pair of "DOI ›" links) on any place-check citing more
  than one study -- a sighted person can tell them apart by the title printed just above each, but a screen-reader
  user moving through links would hear "PubMed, link" twice with no way to know which study either one opens. Fixed
  in `CheckCard.tsx`: each link gets an `accessibilityLabel` naming its study whenever there's more than one.

Neither was caught by the automated walk itself (both are *content* collisions -- technically two different strings,
"PubMed ›" is not literally repeated with the name-conflict check tuned to catch it until it's actually rendered
twice on one screen, which only a real browse surfaces) -- a reminder that the script is a floor, not a ceiling; see
[feedback: audit every screen](../../CLAUDE.md).

## 4. Ease of use and score calibration

Walked the Dashboard, Score, Places, and Journey screens for a person with a rich, 84-day history (94/100,
"Excellent," 89% of the picture visible). The score screen states plainly, above the number, that it's "a personal
dashboard reading, not a diagnosis"; coverage is shown next to the score rather than hidden; the eight-week trend
strip (92, 93, 93, 93, 93, 94, 94, 94) shows exactly the kind of calm, small day-to-day movement the simulation's
own invariants require, not a volatile number. No usability issues found in this pass beyond the two UI bugs above
(section 3), which did directly touch "ease of use" -- a duplicated sentence and an ambiguous pair of links are
usability defects as much as accessibility ones.

## 5. Stickiness, read against this project's own calm-by-design rule

This project's own invariant 7 (CLAUDE.md, agreed 2026-09-28) is explicit: no streaks, points, levels, badges or
leaderboards, the plant never wilts, reminders and learning moments start off, and nothing is tuned to bring people
back more often. So this section checks *whether that promise actually holds on screen*, not whether the app could
be made stickier.

**Checked and holds up:**

- Grepped every screen and component for nagging/guilt/FOMO language (*"haven't logged," "miss you," "come back,"
  "don't forget," "falling behind," "it's been a while"* and similar) -- the only genuine hits are a recall
  question's own spaced-repetition copy ("ideas... come back on their own") and an OAuth-flow instruction ("come
  back and tap Refresh"), neither of which is a nag. The Dashboard explicitly tells the person, in its own words:
  *"No daily reminders, no 'you haven't logged in' nudges, no badges -- only air quality near you, when location
  alerts are on."* That's not just a design intent sitting in a test file; it's stated to the user, on screen.
- The one notification path that exists (a daily check-in reminder) is correctly gated behind the person actively
  choosing a time during onboarding (`checkInTime !== "off"`); the default (`CALM_DEFAULTS.checkInTime`) is `"off"`,
  and nothing schedules anything unless that default was changed.
- `calm.test.ts` already holds the line in code (no `\bXP\b`, streak counters, "Boss" steps, level numbers, or
  badge-unlock text anywhere in `src/screens` or `src/components`) and the plant provably never shows a need or
  drops below "thriving" regardless of how long the app was closed (checked across 0-365 days away, every
  combination of steps done and learning days, in `plant.test.ts`).

**A judgment call, not a bug -- flagged rather than changed unilaterally:** the Journey hub and Dashboard both show
the three stages (Tutorial, Explore, Mastery) as fraction counters in pill badges -- "Tutorial 11/11," "Mastery
5/6." These are plain counts, not points, and they pass `calm.test.ts`'s letter exactly (no XP, no numeric "Level,"
no badge-unlock language) -- but visually, a row of three pill-shaped fraction badges is closer in *shape* to a
game's progress tracker than to the plain "15 of 21 checks meet their reference" style used elsewhere on the same
screen. Worth your own look rather than a change I'd make on my own judgment: keep as-is (they're honest counts, not
manipulation), restyle to read more like a plain status line, or drop the fractions and keep just the stage names.
